Razorpay AI Buildathon · Track 03

A failed payment is a decision, not a retry.

ResilientMesh is the deterministic control plane between a language model and a merchant's money. The model may describe what went wrong. It may never decide what happens next, never name an amount, and never move a rupee. Fourteen invariants do that, and every one of their refusals lands in a ledger you can verify without trusting the system that wrote it.

Real

  • Embedded PostgreSQL, Redis Streams, the outbox relay, the worker, the gatekeeper and the executor: production code paths, not a demo build.
  • Every decision, and the rule that permitted or refused it.
  • The audit ledger, its hash chain and its Merkle root.
  • The LIVE inference calls, over the network, at temperature 0.
  • Every count and timestamp, read from the running system's own database.

Simulated

  • The payments. A simulator serves Razorpay's schemas, signs real HMAC webhooks and emits real decline codes against real Indian issuer codes. No customer, and no rupee, is real.
  • So every money figure is simulated money. Summed honestly from the attempts table; it measures the policy, not a merchant's revenue.
  • The clock. Waits before a scheduled retry are compressed. Regulatory delays never are, and the factor is recorded in the ledger.

01 / PROBLEM

Razorpay already ships five recovery agents. This is not a sixth.

Agent Studio has Subscription Recovery, Revenue Drop Detector, Auto-Capture, RTO Shielder and Dispute Auto Responder. Making an agent act is the solved part. Letting it act on a regulated merchant's money is not.

The blocker is liability

When an agent retries a customer's mandate, someone has to show afterwards that it was allowed to. Today that means mining logs written by the same system that took the action.

A rationale is not evidence

A model's explanation is a post-hoc narration, not a cause. It is generated after the decision, by the thing being audited, and it changes if you ask twice.

So the output is a proof

Every action and every refusal names the invariant responsible and lands in a hash-chained ledger with a Merkle root, so one payment can be proved to a bank without handing over the rest.

Demonstrated on the hardest case in the track: RBI-regulated recurring mandate recovery, where a wrong retry is not a bad outcome but a regulatory breach.

03 / REFUSALS

The half that matters is what it would not do

A recovery system that only logs its successes cannot be audited. Every abstention below is a ledger entry naming the rule that caused it. Rules that never fired are shown with a zero rather than hidden, because a table of only the rules that triggered would let you assume the rest are decorative.

All fourteen are pure functions of state, proved exhaustively rather than sampled: 510,720 reachable mandate states, 8,390,192 transitions, 0 violations. Re-derive it with go run ./cmd/modelcheck.

How the digest is computed

Each entry commits to its predecessor. Fields are absorbed length-prefixed, an 8-byte big-endian length then the bytes, rather than concatenated. Naive concatenation would let an attacker controlling two adjacent fields forge a collision by shifting the boundary between them. 

h := sha256.New()
absorbUint(h, uint64(e.Seq))
absorbStr(h, e.IncidentID)
absorbStr(h, string(e.Kind))
absorbStr(h, e.Actor)
absorb(h, e.Detail)
absorbUint(h, uint64(e.At.UTC().UnixNano()))
absorbStr(h, e.PrevHash)

The problem a hash chain alone does not solve

Checking one entry against a chain means walking every entry before it. A merchant disputing a chargeback cannot hand a bank hundreds of unrelated payment records, and would not be permitted to if they wanted to. So the ledger also carries a Merkle root, and any single entry can be proved under it with about ten sibling hashes that disclose nothing about any other payment.

    06 / ENGINEERING

    How it is built, and what broke while building it

    The depth lives here rather than above, so the argument stays readable.

    Path of one failed payment

    Signed webhookHMAC verified before anything parses it
    Ingestincident, outbox row and audit entry in one transaction
    ↓
    Outbox relayat-least-once, backs off through an outage
    Redis Streamsconsumer group, dead-letter queue
    ↓
    DiagnosisLIVE, then REPLAY, then HEURISTIC
    Gatekeeper14 invariants, all deterministic
    ↓
    Executorthe only component that spends money
    Ledgerhash chain plus Merkle root

    Decisions that are not the model's to make

    DecisionWhy not the model
    Anything at allThe gatekeeper is 14 pure functions. Model output is an input to it, never a substitute for it.
    MoneyAmounts are copied from the signed payload.
    Regulatory timingRBI cooling and pre-debit notice are arithmetic on timestamps. A model 99 percent right about a legal minimum is unusable.
    Retry budgetsBounded arithmetic, not judgment.
    The ledgerWritten by the code that acted, hashed by a function with no configuration.

    Enforced by types, not by prompt wording

    DiagnosticContext, sent to the model Allowlisted and bucketed. No PII, no customer id, no exact amount. A success rate arrives as "0 to 20 percent", never as a number.
    ↓
    DiagnosticProposal, returned by the model Advisory. It has no amount field at all, not a validated one, no field. Provenance carries json:"-".
    ↓
    Gatekeeper Fourteen pure functions of state. May downgrade or refuse any proposal. May never upgrade one.
    ↓
    SanitizedCommand Authoritative. Its amount is copied from the signed payload.

    Three consequences

    • A model returning {"mode":"LIVE"} cannot forge its own tier, because provenance fields are unmarshalable and stamped in-process.
    • A model cannot change a sum, because the proposal type has no field to carry one.
    • A prompt-injected action cannot become a valid action, because the parsers fold ASCII only. That one was a real bug; it is defect 3.

    Every one of these is testable in chapter 04, against the same code.

    Tier 1 LIVE

    A hosted model, used when evidence genuinely has to be weighed: an ambiguous decline code, an issuer degrading, a downtime notice that may or may not be the cause. Temperature 0, JSON only, hard timeout.

    Tier 2 REPLAY

    1,080 digest-keyed cassettes. Identical evidence replays an identical answer, so a reviewer with no API key still sees model-grade decisions and the benchmark stays reproducible.

    Tier 3 HEURISTIC

    A deterministic classifier for codes whose cause the taxonomy already states. card_expired does not need a language model, and paying one to say so is the worse engineering decision.

    Why this page is static

    A hosted demo proves the system runs on someone else's computer. A free Space sleeps after inactivity, so a reviewer's first click can land on a cold start that reads as broken, and hosting it would put a webhook endpoint and an operations console on the public internet for no evaluative benefit. So the page carries the record, plus the two things a static page can genuinely prove: the ledger's integrity and the gatekeeper's behaviour, both computed on your machine.

    What it solves

    Failed payments in India are recovered today by blind retries that burn gateway fees, annoy customers, and on recurring mandates can breach RBI's e-mandate rules. ResilientMesh decides each failure on evidence, refuses the ones no retry can fix, obeys the regulatory constraints as hard invariants rather than prompt instructions, and emits a portable proof of every decision including the refusals.

    Anyone can make an agent act. The hard part is proving, afterwards, that it was allowed to.
