Razorpay AI Buildathon · Track 03 · AI Revenue Recovery

A failed payment is a decision, not a retry.

ResilientMesh is the deterministic control plane that sits between a language model and a merchant's money. The model may describe what it thinks went wrong. It may never decide what happens next, never name an amount, and never move a rupee. Fourteen deterministic invariants do that, and every refusal is written to a tamper-evident ledger beside every action.

Every number on this page was read out of a running system's PostgreSQL database during one execution, then exported. Exactly one thing is computed live, in your browser: the audit chain's SHA-256 digests, from the same bytes the ledger hashed. You do not have to take that on trust either. What is real here

  • The system. Embedded PostgreSQL, Redis Streams, the outbox relay, the worker, the gatekeeper and the executor are the production code paths, not a demo build.
  • Every decision, and the rule that permitted or refused it.
  • The audit ledger and its SHA-256 hash chain, which you can re-derive on this page.
  • The LIVE inference calls. This run used a hosted model over the network, at temperature 0, and the tier that answered is recorded on each decision.
  • Every count, amount and timestamp, read out of the running system's own database.

What is simulated

  • The payments. Traffic comes from a Razorpay simulator that serves Razorpay's schemas, signs real HMAC webhooks and emits real decline codes against real Indian issuer codes. No customer, and no rupee, is real.
  • Therefore every money figure on this page is simulated money. It is summed honestly from the attempts table of this run, and it measures the policy, not a merchant's actual recovered revenue.
  • The clock. Waits before a scheduled retry are compressed so the loop closes while you watch. Regulatory delays are never compressed, and the compression factor is recorded in the ledger.

This distinction is stated up front rather than in a footnote because a recovery system that overstates its own numbers has failed at the thing it exists to do. The claim being made is about the decision-making, and that part is real.

Problem taste

Razorpay already ships recovery agents. This is not a sixth one.

Agent Studio already has Subscription Recovery, Revenue Drop Detector, Auto-Capture, RTO Shielder and Dispute Auto Responder. Building a seventh variation of those would be building the part that is already solved. The unsolved part is the one that stops any of them from being shipped to a regulated Indian merchant.

The question a merchant asks

"Your agent retried my customer's mandate. Prove it was allowed to, prove it did not change the amount, and show me the record. The one that would still be trustworthy if someone had database access."

What most builds answer

A log line and a model's rationale. Both are written by the same system that took the action, and neither is evidence: an LLM's explanation is a post-hoc narration, not a cause.

What this answers

The rule that permitted it, by name. The amount, provably carried from the signed webhook and never from the model. And a hash-chained ledger you can verify without trusting the system that wrote it.

Positioned honestly: ResilientMesh is the layer that makes shipping the first five agents defensible, demonstrated on the hardest case, which is RBI-regulated recurring mandate recovery. There a wrong retry is not a bad outcome. It is a regulatory breach.

The trust boundary

DiagnosticContext, sent to the model Allowlisted and bucketed. No PII, no customer identifier, no exact amount. A success rate arrives as "0 to 20 percent", never as a number.
↓
DiagnosticProposal, returned by the model Advisory. It has no amount field at all, not a validated one, no field. Provenance carries json:"-", so a reply of {"mode":"LIVE"} cannot forge its own tier.
↓
Gatekeeper Fourteen invariants, pure functions of state. It may downgrade or refuse any proposal. It may never upgrade one.
↓
SanitizedCommand Authoritative. Its amount is copied from the signed payload, which is why the model literally cannot change a sum.

Proved by exhaustive model checking rather than by sampling: 510,720 reachable mandate states, 8,390,192 transitions, 0 violations.

    AI judgment

    The right tool in the right place, and where a model was refused

    Three inference tiers, tried in order, with the tier that answered recorded on every decision. A model that cannot be reached is not an outage. It is a degradation the system is designed for.

    Tier 1  LIVE

    A hosted model, used when evidence genuinely has to be weighed: an ambiguous decline code, an issuer degrading, a downtime notice that may or may not be the cause. Temperature 0, JSON only, hard timeout.

    Tier 2  REPLAY

    1,080 digest-keyed cassettes. Identical evidence replays an identical answer, so a reviewer with no API key still sees model-grade decisions and the benchmark stays reproducible.

    Tier 3  HEURISTIC

    A deterministic classifier for codes whose cause the taxonomy already states. card_expired does not need a language model, and paying one to say so is a worse engineering decision than a lookup.

    Where a model was deliberately not used

    • Deciding anything. The gatekeeper is 14 pure functions. A model's output is an input to it, never a substitute for it.
    • Money. Amounts are copied from the signed payload. The proposal type has no amount field to carry one.
    • Regulatory timing. RBI's cooling window and pre-debit notice are arithmetic on timestamps. A model that is 99 percent right about a legal minimum is 100 percent unusable.
    • Retry budgets and backoff. Bounded arithmetic, not judgment.
    • The ledger. Written by the code that acted, hashed by a function with no configuration.

    How the digest is computed, exactly

    Each entry commits to its predecessor. Fields are absorbed length-prefixed, meaning an 8-byte big-endian length and then the bytes, rather than concatenated. Naive concatenation would let an attacker who controls two adjacent fields forge a colliding entry by shifting the boundary between them.

    // internal/domain/records.go, the Go the ledger actually runs h := sha256.New() absorbUint(h, uint64(e.Seq)) absorbStr(h, e.IncidentID) absorbStr(h, string(e.Kind)) absorbStr(h, e.Actor) absorb(h, e.Detail) absorbUint(h, uint64(e.At.UTC().UnixNano())) absorbStr(h, e.PrevHash)

    This page reimplements those seven lines against crypto.subtle and runs them over the exported bytes. The detail column travels base64-encoded and is decoded here, so what you see expanded is byte for byte what the digest commits to. A page that displayed a re-serialised copy would be verifying something other than what it showed you.

    Failure recovery

    What broke, and what I did about it

    Nine real defects in this codebase, found during this build. None of them were found by reading the code. Each names the technique that caught it, because the technique is the transferable part. The last one is still open.

    1. MODEL CHECKING 58,512 violations to 0
      Two gatekeeper defects that 20,000 property-test cases missed. RBI_AFA_CEILING was specified and never implemented, so a mandate above ₹15,000 would have been retried without a fresh authentication factor. That is a regulatory breach, not a suboptimal choice. EXECUTABLE_NAMES_A_RAIL failed at 29,952 states: the gate emitted an executable command naming no rail. The property corpus could never generate an instrument refresh, so 20,000 draws of the wrong distribution found nothing. Property testing samples. Model checking enumerates.
    2. CONSUMER REVIEW 5 fail-open contracts
      Five fail-open defects in my own frozen contracts. The worst: Validate() accepted NaN as a confidence score. Every ordered comparison against NaN is false, so conf < floor waved it straight through and every downstream check read it as maximum confidence. Also a failure class that defaulted to recoverable, and provenance fields a model could set to forge its own tier.
    3. UNICODE closed sets were not closed
      Case folding admitted non-members into every closed set. strings.ToUpper applies Unicode case mapping, and U+017F (ſ) uppercases to a plain ASCII S. So ParseAction("AſYNC_EXPONENTIAL_RETRY") returned a valid action. These parsers sit directly on the model boundary, so a prompt-injected reply could smuggle a fabricated action past the abstention the contract promises. Replaced with ASCII-only folds.
    4. BOOTING IT 12 diagnosed, 1 acted on
      The offline path recovered nothing. Every unit test passed and every component was individually correct. Running the whole thing showed twelve incidents diagnosed and one acted on: the deterministic tier had no rule for the soft decline codes, so with no API key, which is every reviewer by design, a recovery system recovered nothing.
    5. BOOTING IT a comment described a component that did not exist
      Deferred recoveries were silently dropped. The worker marked a delayed command SCHEDULED and acknowledged the message. A comment claimed a scheduler would collect it. There was no scheduler. The ledger recorded a correct decision that never happened, and every report looked right. Fixing it exposed a second defect immediately behind it: a swept incident recomputed its backoff and deferred itself forever.
    6. SIMULATION NO_DOUBLE_PROCESSING
      A retried write that double-counted real money. The attempt-commit path is retried on purpose, but the retried block was not idempotent: a failure after RecordAttempt re-ran it and inserted a second row for the same attempt. The table had an index on (incident, attempt) but no uniqueness, so it double-counted a gateway fee and inflated every recovery measurement, in the direction that flatters the system.
    7. SIMULATION NO_EVENT_LOST, 20,434 rows
      A transient broker outage permanently destroyed events. The relay parked a row on its first publish failure, which made the eight-attempt budget unreachable, and the claim itself charged an attempt, so an outage exhausted every budget in the table. The relay's own comment stated the correct principle and the code did the opposite. It now probes the queue and hands the batch back uncharged when the broker is down.
    8. RUNNING IT TWICE found while building this page
      The demonstration poisoned its own next run. Act 5 deliberately forges a ledger row and does not repair it, and the next run inherited that forgery through a reused data directory, failing at boot with a chain broken before it had written anything. The fix was to give the demonstration its own database and empty it on every run, which is also what makes "the run is a pure function of its seed" true on the second run instead of only the first. Adding a repair path for one's own audit trail would have been the wrong fix, because a system that can repair its audit trail does not have one.
    9. OPEN, NOT FIXED reproducible, left failing on purpose
      The reconciler amplifies during an outage. A parked outbox row is not PENDING, so the reconciler treats its incident as stalled and inserts a replacement, which parks too. 20,434 rows from 400 incidents, all of it write amplification aimed at a queue that is already down. Two fixes were attempted and both reverted: one traded a loud failure for a silent one, and the other stopped the run draining for reasons I did not fully characterise. A verification harness edited until it agrees with the system is not a harness, and a fix I cannot explain is not a fix. Reproduce it with go run ./cmd/meshsim --seed 20260904 --incidents 400. It is documented rather than hidden.
    Build quality

    Run the real thing in about two minutes

    One command. No Docker, no cloud account, no payment credentials, no API key. It starts embedded PostgreSQL and a Redis-protocol server inside the process, drives a scripted bank outage through the real system, and narrates what it is doing while every number is read back out of the database.

    # Go 1.25 or newer is the only prerequisite. $ git clone https://github.com/vighriday/ResilientMesh-Razorpaybuildathon $ cd ResilientMesh-Razorpaybuildathon $ go run ./cmd/meshdemo # Optional. Watch the LIVE tier decide instead of the deterministic one. # A Groq key is free and needs no card: https://console.groq.com/keys $ echo "MESH_LLM_PROVIDER=groq" >> .env $ echo "MESH_LLM_API_KEY=your_key_here" >> .env $ go run ./cmd/meshdemo

    Check the claims independently

    $ go run ./cmd/meshctl selftest # the same loop as a pass/fail gate $ go run ./cmd/modelcheck # 510,720 states, 0 violations $ go run ./cmd/meshsim --seed 42 # deterministic simulation, fault injection $ go test ./... -count=1 # the full suite $ ./scripts/judge.sh # every gate, with a written report

    Why this page is static

    A hosted demo proves the system runs on someone else's computer. A free Space sleeps after inactivity, so the first click can land on a cold start that reads as broken. And hosting it would put a webhook endpoint and an operations console on the public internet for no evaluative benefit.

    So the strongest artefact is the command above, running on your machine against your database. This page is the record of it, plus the one thing a static page can genuinely prove: cryptographic verification that needs no server at all.

    What it solves

    Failed payments in India are recovered today by blind retries that burn gateway fees, annoy customers, and on recurring mandates can breach RBI's e-mandate rules. ResilientMesh decides each failure on evidence, refuses the ones no retry can fix, obeys the regulatory constraints as hard invariants rather than as prompt instructions, and leaves a tamper-evident record of every decision including the refusals.

    The whole argument in one sentence: anyone can make an agent act. The hard part is being able to prove, afterwards, that it was allowed to.
